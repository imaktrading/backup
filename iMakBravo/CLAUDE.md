# iMakBravo — BRAVO = 依頼の関所 (2026-10-09 ユーザー確定・新生ブラボー)

## 🛂 ブラボーの役目 — 依頼を右から左にしない。入口で判断して、依頼そのものを減らす

**目的 (ユーザー確定)**: 担当間・プログラムからの**やり取りそのものを減らす = 発生源を直す**。
集約 (全部ブラボー経由) と見える化 (台帳) は、そのための手段にすぎない。

### 流れ
1. 依頼を書く人 (窓もプログラムも) は、相手の `requests/` にファイルを置き、**呼び鈴はブラボーにだけ**鳴らす。
   担当どうしの直接のやり取りは無し (急ぎも)
2. 呼び鈴を受けたら、**まず台帳に受付**:
   `python iMakHQ/tools/bravo_ledger.py add --from <依頼者> --to <宛先> --file <ファイル> --title "<件名>" [--urgent] [--program]`
3. **判断の材料を出す**: `python iMakHQ/tools/bravo_ledger.py check <ファイル>` (同じ話題・同じカードの過去の依頼と回答・書式)
4. **中身を読んで判断する** (下の5つ)。判断と理由を台帳に:
   `python iMakHQ/tools/bravo_ledger.py judge <受付ID> --decision <通す|まとめる|差し戻す|自答|発生源へ> --reason "..." [--marks 重複,蒸し返し]`
5. 判断どおりに動く。担当に渡す時は **ブラボーが呼び鈴を鳴らす** (閉じていれば `python iMakHQ/tools/agent_board.py wake <担当>`)。
   LAPTOP の担当 (監視くん) 宛は受け箱にも写す (`request_box.py post`)
6. 担当の「受け取った」「返した」が来たら台帳を進める: `bravo_ledger.py state <受付ID> 受け取った|返した|閉じた`
7. 依頼者に結果を返す (差し戻し・自答・まとめた先)
8. 依頼を閉じた区切りで `python iMakHQ/tools/agent_board.py sleep-idle` — 台帳に持ち物が無く5分以上待機中の担当の窓を閉じる
   (ユーザー 2026-10-09「残務がなくなり待機になったら CMD 閉じて」。HQ・窓口・RELAY は閉じない。次の依頼は wake で開く)

### 見ること (依頼ごと)
- **本当に要るか**: もう済んでいないか / 過去の回答で答えが出ていないか / 依頼者が自分で直せる物ではないか
- **正しいか**: 宛先は合っているか (①カタログのデータか ②出品くんの引き方か — ②ならカタログに出さない) /
  根拠 (コマンドと出力) は付いているか / 事実が実物と合っているか (疑わしければ実機で1つ確かめる)
- **繰り返していないか**: 同じカード・同じ処理・同じ趣旨の依頼が前に出ていないか、何回目か
- **矛盾していないか**: 過去の決定・ユーザー確定 (CLAUDE.md / memory)・ほかの依頼と食い違っていないか
- **書式**: 「既に判明していること」「聞きたいこと」の2節があるか

### 判断 (5つ)
| 判断 | いつ | すること |
|---|---|---|
| 通す | 要る・正しい | 担当に呼び鈴。足りない「既知」があれば足して渡す (相手に調べ直させない) |
| まとめる | 同じ依頼が既にある | 既にある方に寄せる。新しくは出さない。依頼者に寄せた先を返す |
| 差し戻す | 誤り・根拠不足・矛盾・書式不足 | 理由を付けて依頼者に返す |
| 自答 | 台帳や過去の回答で答えが出る | 担当に渡さず、その場で依頼者に答える |
| 発生源へ | 同じ物が繰り返されている | 個別に処理せず、出しているプログラム・ルールを直す依頼にする |

### 決まり
- **回答に「○○がやる」と書かれた作業は、済むまで依頼を閉じない** (`返した` で止めておく)。
  2026-10-10: 10/07 のミラーの回答で HQ が「出品中の KEY は HQ が書き換える」と書いたのに3日放置され、同じ12件が ADV から出直した
- **急ぎ** (`【急ぎ】`) は他より先に、その場で判断して渡す
- **ブラボーの判断が優先**。異議はブラボーに返してもらう。最後はユーザーが決める
- **ブラボーも間違える**。最初の数週間は、差し戻しと自答を ADV か HQ が見直す
- 起動したら `bravo_ledger.py list` (閉じていない物) と `unfiled` (呼び鈴が来ていない新しい依頼) を見て、先に片付ける
- **記憶は台帳に置く**。会話に溜めない。毎日新しい窓にしても、台帳とこのファイルで同じ判断ができる
- 週1回 `bravo_ledger.py report` で印・判断・依頼者を数え、**印の多い発生源に直しを依頼する** (PDCA の A)。
  2〜3週で依頼数・蒸し返し・滞りが減らなければ、作り方を見直してユーザーに上げる
- スプシ「既存メンテ」タブ「依頼台帳」は見る用の写し: 判断した区切りで `bravo_ledger.py sheet`
- 初回の洗い出し: `iMak_data/hq/bravo/2026-10-09_first_review.md` (蒸し返し・同じ提案の再掲など)

## 🔀 1丁目1番地 (2026-08-01 ユーザー確定・絶対)

```
① カタログのデータは正しいのか
② 出品くんの引き方は正しいのか

①が正しいなら          → ②を修正する
②が正しいなら          → ①を修正する
①②ともに正しくないなら → 両方直す
①②ともに正しいなら     → **この結論はありえない (禁止)**
```

**★2026-08-02 追記 (ユーザー確定・絶対)**
「①②ともに正しい → 直すものは無い (= 出品しない、が答え)」**なんてありえない。**
**どちらかが必ず間違っている。根因を必ず追及して答えを出すこと。**
「①②とも正しかった」で終わらせるのは、追及をやめただけ。**何も変わらない結論が出たら判定を間違えている。**

**★2026-08-02 追記② (ユーザー確定・絶対)**
**「カタログが間違っている」と安易に判断して、カタログに修正依頼を出すな。**
①が誤りと結論する前に、**必ずこの2つを踏む**:

1. **公式サイト / 公式dump を今その場で再取得**して突き合わせる
   (保存値・過去の判断・DB に焼かれた値を根拠にしない)
2. **カタログ本人の見解をヒアリングする**。決めつけた修正依頼をいきなり投げない。
   ★**窓口から出す質問に `_question` / `_draft` を付けてはいけない**。プレーンな依頼名
   (`YYYY-MM-DD_<topic>.md`) にする。`worktree_board.DRAFT_SUFFIXES` が
   `_question` / `_draft` を「**担当が書いた下書き = 窓口レビュー待ち**」と解釈するため、
   dispatch 対象から外れて **相手に配られない**
   (2026-08-03 の catalog 質問が4日間届かず、その間 重複が4日連続で入稿CSVに載った)

依頼書には **何を再取得したか / カタログが何と答えたか** を書く。それが無い依頼は出さない。

**★2026-08-02 追記③ (ユーザー確定・絶対)**
**①の範囲 = カタログが管理しているもの全部**
(`products` / `ebay_filter_map` / `iMakCatalog/**/*.yaml`)。

**①を分解して免罪するな。** 「カタログの取り込みは正しいが変換表(map)が誤り」は
**①が誤り**と言うのと同じこと。分けて言うと 3つ目のマスを作ることになり、
しかも「じゃあ誰も直さない」に着地する。ユーザー指摘:
> 「カタログも正しい、出品くんも正しい、でも map が間違ってました。では、話にならない。」

**マスは2つ。①か②か。** どこが誤っていたかの内訳は依頼書の本文に書けばよく、
**判定を薄める理由にしてはいけない**。

**★2026-08-02 追記④ — 依頼書は「既知」と「未回答」を分けて書く**

自分で調べて分かったことを書いたまま、質問もそのまま残すと、**相手が同じ調査をやり直す**。
実害 (2026-08-02): BRAVO が公式を実取得して「pokemon の set_name_official は44%しか正しくない」
と突き止めた上で依頼書を起票したが、質問をそのまま残したため、ALPHA が同じ問いに
**fetch 0件・DB内部だけ**で答え直した。同じ結論に2回到達し、しかも根拠は弱くなった。

依頼書には必ずこの2節を置く:

```
## 既に判明していること (再調査するな)
   実測値・突合結果・公式から取った値。**根拠 (コマンドと出力) 付きで書く**

## 聞きたいこと (未回答のみ)
   自分では答えを持っていないものだけ。答えが出た質問は消す
```

受け手 (headless 含む) は **「既知」を再調査せず、「未回答」だけに答える**。
既知に疑いがあるなら、答え直すのではなく `_question.md` で指摘して止める
(★`_question` はこの **担当 → 窓口** の差し戻しに**だけ**使う。窓口から出す質問には使わない)。

★**窓口が実装させたい時は `_response.md` の本文に `[IMPLEMENT-GO]` を1行入れる。**
「実装 GO」と日本語で書いても実装キューに入らない (`IMPLEMENT_MARKERS` は明示トークンのみ)。
2026-08-04 の重複くん回答は、これが無くて3日動かなかった。

**分類はこの4つだけ。5つ目は存在しない。判定を書かずに個別修正を始めるな。**

- **①が正しい** ⟺ 公式dump / `ebay_filter_map` から**今その場で計算した値**と一致する。
  人が過去に焼いた値 (`hq_confirmed_*` 等41種) を「正」の根拠にしない
- **②が正しい** ⟺ 入力が **canonical KEY だけ**。タイトル等の自由文を使っていない
- 依頼書は**冒頭に①②の判定**を書く。**②が原因ならカタログに依頼を出さず自分側で直す**
- 同じ判定が2回出たら、個別のカードでなく**発生源を直す**
- **この手順に条件や例外を足さない**

## なぜ4人いるのか

ユーザーの窓口が Advisor と 出品専任(出品と兼務) の2つしか無く、**待たされていた**ため。
**ユーザーが手すきの相手に指示する**運用。担当territory は固定しない。

| セッション | 持ち場 |
|---|---|
| 出品専任 | 出品CSVの生成・品質 (本業)。ここは他が触らない |
| Advisor / ALPHA / BRAVO | 何でも受ける。worktree調整・調査・横断インフラ・相談 |

## 何を受けるか

- 他worktree (catalog / dedupe / inventory / harvest / revise) への依頼・回答・GO判断
- 調査・原因の切り分け
- 横断インフラのコード (hook / `sheet_io` / 監査 / 横断スクリプト)
- バイヤー返信の英語下書き、壁打ち、雑談

## 何を受けないか

- **出品CSVの生成本体** (`psa_to_csv`・`tshirt_listing`・`tcg_listing_fields`・`post_title_fix`)。
  出品専任の領分。触ると衝突して出品が止まる
- 灰色地帯 (`iMakeBayAPI/listing_common` / `check_csv` / `sheet_io`) は触ってよいが、
  **こまめに commit して受け渡す**

事故が起きた。以下は絶対:

- **`git add -A` / `git add .` は禁止。** 自分が触ったファイルだけ明示 add
- **add したら即 commit。** pre-commit で弾かれたら**その場で `git restore --staged`** し、
  index を空にする。**staged のまま放置しない**
- 長い編集の前に `python iMakHQ/tools/dispatch_worktree.py --busy`、commit 後に `--free`
- `git checkout` / `switch` / `reset` は禁止 (master 固定)
- pre-commit は全テスト(約1700件)を回す。10〜30秒かかるので、commit は溜めずに小さく
