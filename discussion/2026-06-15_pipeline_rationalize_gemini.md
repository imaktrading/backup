シニア設計レビュアーのGeminiです。iMak Trading Japan様の絶対前提「間違った内容で出品しない(Precision 100%)」「キャンセル厳禁」「市場ゲート必須」を最優先事項として、新コア導入後のPSA出品パイプラインをレビューしました。

忖度なく、本当に必要なチェックと、安全に削減できる重複を峻別し、理想的な構成を提案します。

---

### 1. 本当に意味のあるチェック(残すべき)

| ステップ | 固有価値 (このチェックがなければ防げないリスク) |
| :--- | :--- |
| **B. HTML目視同定確認(人)** | **誤同定の防止。** システムによるカード特定の最終正当性を人間が保証する最重要関門。 |
| **H. check_csv (市場ゲート)** | **価格逸脱によるビジネスリスク防止。** 高すぎて売れない在庫の出品を防ぐ必須のビジネスルール。 |
| **K. dedupe_excluder** | **重複出品の防止。** eBayポリシー違反や在庫管理の混乱を避けるための必須チェック。 |
| **L. write-keys-from-csv** | **将来の重複チェック/在庫管理の基盤。** この記録がなければKの重複チェックが機能しない。 |
| **N. post_no_go_sentinel** | **運用効率化。** NO-GO対象を記録し、無駄な再処理や原因不明のエラーを防ぐ。 |
| **O. 最終CSV監査くん** | **独立した最終成果物監査。** パイプライン全体を通して生成された最終CSVを客観的に評価し、継続的改善(カタログ修正依頼/PDCA)に繋げる。 |

### 2. 継ぎ足し重複で削れる/統合すべきもの

| 対象ステップ | 削減/統合の理由 |
| :--- | :--- |
| **G. 生成時セルフ監査** | **HとOに完全に包含される。** DRY-RUNでの報告は後続のH(判定)やO(最終監査)で実施されるため冗長。**Oに統合すべき。** |
| **H. (Claude AI総合レビュー)** | **新コアと役割が衝突する。** 新コアが決定論で生成するため、AIによる推測や改善提案は「Precision 100%」の原則に反するノイズ。安全に**完全削除可能。** |
| **3AIタイトル合議** | **新コアにより陳腐化。** 決定論タイトル生成に移行したため、既に実質不使用。**完全削除可能。** |
| **M. post_psa_review** | **Bのverify→buildプロセスで代替済。** 設計上、二重実行が防止されており、明確に不要。**完全削除可能。** |
| **市場ゲート/SEO計算 (G, H, O)** | **複数回実行は非効率。** 市場ゲート(NO-GO判定)は除外(I)の直前に1回、SEO等の監査は最終成果物(O)に対して1回で十分。**H(判定)とO(監査)に役割を明確化し集約。** |

### 3. 理想の最小パイプライン順序

現行のステップを再編し、以下の順序を提案します。重複をなくし、各ステップの責務を明確化しました。

1.  **A. PSA scrape**: データ取得
2.  **B. HTML目視同定確認(人)**: **[関門1]** カードの正しさを人間が確定
3.  **C. build_row + 新コアoverride**: 確定情報から決定論でデータ行を生成
4.  **E. 市場価格取得 → StartPrice 決定**: 価格情報を付与
5.  **(統合) Pre-flight Check & Exclude**: **[関門2]** 出品可否をシステムが最終判定・除外
    - **H'. 市場ゲート判定**: (旧H) NO-GOを判定
    - **J'. タイトル後処理**: (旧J) 文字数paddingなど最終整形
    - **K'. 重複チェック**: (旧K) 既出品KEYと照合
    - **I'. 物理除外**: 上記判定(NO-GO/重複)に基づき、対象行をCSVから除外
6.  **F. 最終CSV書き出し**: 入稿が確定したCSVを生成
7.  **(統合) Post-flight Logging & Audit**: 出品確定後、記録と改善アクションを実行
    - **L. write-keys-from-csv**: 最終CSVから出品KEYを管理スプシに記録
    - **N. post_no_go_sentinel**: 除外されたcertを管理スプシに記録
    - **O'. 最終監査**: 最終CSVと除外ログを元に、SEOメモ/catalog修正依頼/PDCA台帳を生成 (旧G, Oを統合)

### 4. 市場ゲート(価格NO-GO)の集約先

**上記理想パイプラインのステップ5「Pre-flight Check & Exclude」内 (旧Hの責務) に集約すべきです。**

理由は、物理的に行を除外する直前に、ビジネスルールに基づく最終判断を一度だけ行うのが最も効率的かつロジックとして明快だからです。複数箇所での判定は、ロジックの分散を招き、メンテナンス性を低下させます。

### 5. 新コア導入で役割が変わった/不要化したチェック

新コアは「SSOT(社内catalog)からの決定論コピー」であるため、実行時のデータ品質チェックの一部は、**SSOT自体の品質担保**に責務が移ります。

-   **D. eBayフィルタ validate (NFKC正規化/日本語混入blank)**:
    -   **不要化。** 新コアが参照するSSOTの`set_name_ebay`等のフィールドが最初からクリーンであれば、実行時のチェックは不要です。責務はSSOTのメンテナンスプロセスに移管されます。
-   **H. 必須spec空チェック**:
    -   **役割変更。** 「出品データの必須項目が空か」のチェックから、「**SSOT(カタログ)の必須項目が未定義か**」を検知する役割に変わります。これは実行時エラーではなく、`O. 最終監査`で「catalog修正依頼」として報告する方が適切です。
-   **J. post_title_fix (日本語除去)**:
    -   **不要化。** Dと同様、SSOTにeBay用の英語タイトルフィールドを用意すれば、生成時に日本語が混入する余地がなくなります。`文字数padding`のような機械的な整形処理のみ残ります。

### 6. 削ると危険な「独立検証」として残すべきチェック

「自己申告(自身の生成ロジック)を信じない」という観点では、生成ロジックとは独立した外部要因との照合が不可欠です。

1.  **市場ゲート (H)**: 生成データが正しくても、**外部要因である「市場価格」**との比較で不適切になり得ます。これは独立したビジネスルールの検証であり、絶対に必要です。
2.  **重複チェック (K)**: **外部状態である「過去の出品履歴」**との照合です。生成ロジック単体では検知できないため、独立したチェックとして必須です。
3.  **最終CSV監査くん (O)**: パイプライン全体をブラックボックスと見なし、その**最終成果物**を客観的な基準(SEOベストプラクティス等)で評価します。これはパイプライン自体の健全性を監視するメタ的な独立検証として非常に価値があります。

以上のレビューが、より堅牢で効率的なパイプライン構築の一助となれば幸いです。
