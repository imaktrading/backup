## 🔀 1丁目1番地 — カタログ絡みは必ずこの手順で判定してから直す (2026-08-01 確定・絶対)

```
① カタログのデータは正しいのか
② 出品くんの引き方は正しいのか

①が正しいなら          → ②を修正する
②が正しいなら          → ①を修正する
①②ともに正しくないなら → 両方直す
①②ともに正しいなら     → **この結論はありえない (禁止)**
```

**★2026-08-02 追記 (ユーザー確定・絶対)**
「①②ともに正しい → 直すものは無い (= 出品しない、が答え)」**なんてありえない。**
**どちらかが必ず間違っている。根因を必ず追及して答えを出すこと。**
「①②とも正しかった」で終わらせるのは、追及をやめただけ。**何も変わらない結論が出たら判定を間違えている。**

**★2026-08-02 追記② (ユーザー確定・絶対)**
**「カタログが間違っている」と安易に判断して、カタログに修正依頼を出すな。**
①が誤りと結論する前に、**必ずこの2つを踏む**:

1. **公式サイト / 公式dump を今その場で再取得**して突き合わせる
   (保存値・過去の判断・DB に焼かれた値を根拠にしない)
2. **カタログ本人の見解をヒアリングする** (`_question` / `_draft` で先に聞く)。
   決めつけた修正依頼をいきなり投げない

依頼書には **何を再取得したか / カタログが何と答えたか** を書く。それが無い依頼は出さない。

**★2026-08-02 追記③ (ユーザー確定・絶対)**
**①の範囲 = カタログが管理しているもの全部**
(`products` / `ebay_filter_map` / `iMakCatalog/**/*.yaml`)。

**①を分解して免罪するな。** 「カタログの取り込みは正しいが変換表(map)が誤り」は
**①が誤り**と言うのと同じこと。分けて言うと 3つ目のマスを作ることになり、
しかも「じゃあ誰も直さない」に着地する。ユーザー指摘:
> 「カタログも正しい、出品くんも正しい、でも map が間違ってました。では、話にならない。」

**マスは2つ。①か②か。** どこが誤っていたかの内訳は依頼書の本文に書けばよく、
**判定を薄める理由にしてはいけない**。

**★2026-08-02 追記④ — 依頼書は「既知」と「未回答」を分けて書く**

自分で調べて分かったことを書いたまま、質問もそのまま残すと、**相手が同じ調査をやり直す**。
実害 (2026-08-02): BRAVO が公式を実取得して「pokemon の set_name_official は44%しか正しくない」
と突き止めた上で依頼書を起票したが、質問をそのまま残したため、ALPHA が同じ問いに
**fetch 0件・DB内部だけ**で答え直した。同じ結論に2回到達し、しかも根拠は弱くなった。

依頼書には必ずこの2節を置く:

```
## 既に判明していること (再調査するな)
   実測値・突合結果・公式から取った値。**根拠 (コマンドと出力) 付きで書く**

## 聞きたいこと (未回答のみ)
   自分では答えを持っていないものだけ。答えが出た質問は消す
```

受け手 (headless 含む) は **「既知」を再調査せず、「未回答」だけに答える**。
既知に疑いがあるなら、答え直すのではなく `_question.md` で指摘して止める。

**分類はこの4つだけ。5つ目は存在しない。判定を書かずに個別修正を始めるな。**

- **①が正しい** ⟺ 公式dump / `ebay_filter_map` から**今その場で計算した値**と一致する
- **②が正しい** ⟺ 入力が **canonical KEY だけ**。タイトル等の自由文を使っていない
- 依頼書は**冒頭に①②の判定**を書く。**②が原因ならカタログに依頼を出さず自分側で直す**
- 同じ判定が2回出たら、個別のカードでなく**発生源を直す**
- **この手順に条件や例外を足さない**

詳細と経緯: グローバル `~/.claude/CLAUDE.md` の同名節 / `memory/catalog_vs_lookup_triage.md`

## 🛡️ 執行原則 (Step 6: AI協調プロトコル — 2026-04-25 制定)

修正連鎖を断ち切るため、以下を **毎修正前に Claude が自問** すること:

### 3つの呪文（Gemini Round 4 推奨、3AI 全員合意）

1. **「その修正、YAML でできないか？」**
   - ロジック (Python) を汚す前に、`iMakeBayAPI/config/global.yaml` の値追加で済まないか
   - 値が SSOT 経由で読まれているなら、コード変更不要

2. **「この共通化、`if 分岐` を含んでいないか？」**
   - 共通モジュール内に `if category == "TCG"` / `if project == "G-shock"` を書いた瞬間に負債復活
   - プロジェクト固有の差異は **外部から注入されるデータ** として扱う（yaml / 引数）

3. **「Step 6.5 の全テストを回したか？」**
   - TCG の修正でも G-Shock / Mercari / 一番くじ のテストを必須実行
   - pre-commit hook で物理的に強制（commit 拒否される）

### 修正時の指示テンプレ（ユーザー → Claude）

```
変更対象: <ファイルパス>
変更理由: <何を解決するか>
影響範囲: <他に影響しうるモジュール>
追加テスト: <regression を防ぐ test ケース>
触ってはいけない範囲: <既存のロジックで保護したい箇所>
```

### バグ＝テスト追加運用（Step 6 不文律）

- **新しいバグを直す時、必ず1個 pytest を追加する**
- regression test は資産。蓄積すれば修正連鎖は構造的に減る
- テストなしの bugfix commit は pre-commit が拒否（テストが既存だけだと検知できない）
