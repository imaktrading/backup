# PSA 補URL 能動充填・補充サイクル 設計 (2026-07-24)

> 起点: 「出品して在庫切れになったら取り下げるだけ。補充(補URL含む)サイクルを追加すべきでは」
> (ユーザー problem statement)。孤児救済は打ち切り、この設計に集中。

## 一言

**出品が「仕入元1本切れ」で死なないよう、予備の仕入先URL(補URL)を厚く保つ仕組み。**
出品を止めない([[user_goal_daily_correct_listings]])に直結 = 新規を増やさず live維持率↑=露出↑=sell-through↑。

## 設計

### 概要: 夜昼2フェーズ + 監視くん掃除

| フェーズ | 時間 | 中身 | 流用 |
|---|---|---|---|
| ① 夜間スクレイプ | 無人 | 対象(live・補<閾値)を throttle 検索→候補+**画像を永続ディスクキャッシュ** | `psa_resource_gate`検索部 + `psa_research_cache.json` + `_fetch_image` |
| ② 昼の確認 | 有人 | キャッシュから即表示のHTML視覚確証→補URL書込(増分保存・続きから) | `build_restock_html` + `hoju`書込 |
| ③ 掃除 | 監視くん毎cycle | 売切確定の補URLをクリア + 売切日時stamp | watcher(Inventory) |

### 役割分担(排他=書込競合しない)
- **HQ(補URLボタン)** = 空き枠に新供給を**足す**(空き枠のみ・冪等)
- **監視くん(Inventory)** = 売切確定の補URLを**消す**(売切確定セルのみ)+売切日時記録
- **監視くん(既存)** = 補が生きてれば延命(そのまま)

### 対象量・閾値
- **初期** = 補0本の全部(186件)= 一回こっきりの backlog
- **定常** = 補が **≤1本**(既定)に減った分だけ再充填(5本まで)。ホット品=需要ティアで **≤2〜3**。
- **需要ランク**(watch/impr/過去販売)で夜間対象を優先度付け=高需要から厚く。
- 閾値は固定でなく **売切日時churnデータで型番別に自動チューニング**。

### レジューム/中断耐性
- **補URL自体がレジューム状態**: 対象クエリ=「live・補<閾値」→埋めた瞬間クエリから外れる→次セッションは残りだけ。別途「済リスト」不要。
- **増分コミット**: 塊ごと(「この20件を保存」)に補URL書込。いつ閉じても失われない。
- **埋められなかった分**(供給ゼロ/全部違う変種)= cooldown付き skip台帳で一定期間再表示しない([[catalog_missing_auto_request]] の `_record_review_skip` パターン流用)。数日後再挑戦。

### 件数感・目視のやりやすさ
- 進捗バー常時表示(全186/済40/残146)。
- ページ分割(1画面20-30件)。
- 画像は夜に取り切り済=スクロール快適。
- 既存メンテdashboardに「補URL不足 X件」カウンタ。

## ガード(既存原則そのまま)

1. **変種一致**(P-066/P-041 多変種取り違え防止):
   - **単一変種 or `kw_variant_confident` 通過 → 無人auto-seed**(誤変種リスク構造的にゼロの分だけ)
   - **多変種で曖昧 → 自動seedせず人の視覚確証へ**(補URLも誤変種在庫あり→延命→誤カード仕入れ→SNAD/BAN で主URLと同じ危険度)
2. **PSA10 + 新品condition + element-based** 在庫確認。
3. **画像 fail-closed**: 夜にリトライしても取れない候補=`.card.noimg`赤枠で「画像取得不可・要手動」明示 → **目視確定の対象にしない**(見えないカードを人に確定させない)。
4. **監視くん削除 fail-closed**: `is_sold=True`確定時**だけ**補URL消す。取得失敗/uncertainでは消さない([[failclosed_must_skip_not_destructive]]、2026-06-03偽OOS事故の同型)。主URL(col A)はこの経路で消さない。
5. **急増ガード流用**(データ不具合での一斉消去/誤一括防止)。
6. **供給ゼロ ≠ 検索失敗**: 補が取れないのは害なし(そのまま生きる、取下げの引き金にならない)。検索失敗は「不明」でリトライ。本当に枯れた分はデータとして記録。

## カタログ連携(双方向シームレス)

- **読み(既存配線)**: 変種リストは `catalog_variants_for_cardno` が catalog sqlite(SSOT)から引く。KEY=catalog product_id が全システム共通言語([[catalog_ssot_principle]])。
- **書き戻し(追加)**: 検索・確証で「候補なし=要catalog追加」に当たったら黙って推測せず**自動でCatalog修正依頼**([[catalog_missing_auto_request]] パターン、requests dir投入)。
- **自己強化ループ**: 補URLボタンが186件×供給検索で市場を舐める=**カタログ穴の発見エンジン**。違う/候補なし→Catalog依頼→カタログ厚く→matcher精度↑→人手減。

## 効果測定(PDCA / スパイラルアップ)

**新規分析システムは作らない = ファネル流用 + 2フックだけ。**

- **フック1: 補URL状態タグ**(補0本 / ≥1本)を各出品に付与 → ファネルが「補あり vs 補なし」で成績(取下げ率/live日数/成約数)をセグメント。
- **フック2: 救済ログ** = 監視くんが「主死んだが補で延命」した瞬間(既に `raw_status="in_stock@backup#N"` で判別可)を1行ログ。
- **★救済率 = この仕組みの外側ループ**: 救済が少ない=労力の割に無意味→撤退判断。**Phase1と同時に計装して測る**。

### 回すほど賢くなる(Check止まりにせず必ずActへ)
- **「違う」率トレンド**(card/クエリ別)→ 高い=検索クエリ/カタログ変種が悪い → **生成側修正**([[refine_generation_not_audit_firefighting]])
- **「候補なし」率トレンド** → 下がる=カタログ整備進捗の証拠 / 下がらない=依頼未処理検知
- **売切日時→churn率** → **リフィル閾値と夜間優先度を自動調整**
- **前回比トレンド+再発検知** を毎夜ログ([[pdca_spiral_up_expectation]])
- **test化**: 変種一致・fail-closed(画像/skip/削除)・閾値ロジックを pytest(bug→test)

## 未確定・残リスク(正直に)

1. **成否を決める2数字が未測定**: 多変種割合 / 救済率。設計は堅いが**価値はPhase1で測るまで仮説**。
2. **効果が構造的に小さいシナリオ**: 出品が仕入元より先にeBayで売れる/供給がめったに死なない → 救済率低 → limited。前提を崩す唯一のシナリオ。救済率でしか分からない。
3. **2worktree跨ぎ**: 定常ループは HQ+Inventory 両輪必須。段取りで緩和済だが coordination は残る。
4. **人手ボトルネック**: 多変種は毎日人手。定常量が本当に小さいか(閾値設計は示唆するが)未測定=#1に依存。

**設計自身が安く潰せる形**(Phase1薄く→救済率実測→続/撤退が低コスト)= 良い賭け方。
