## 2. なぜ繰り返すのか — 根本原因

**手で書いた値を、誰も検算していない。**

eBay はカテゴリ 183454 の値を公式APIで公開している。

```
Set     2,290語   aspect_mode = FREE_TEXT
Rarity     57語   aspect_mode = FREE_TEXT
```

JSON は既に `C:/dev/iMak_data/catalog/_input/ebay_tcg_filter_lists_api.json` にある。
**しかし461語の変換表はこれを一度も参照していない。**
`whitelist_registry.py` の公式照合は porter / 一番くじ / リール / Tシャツ の4商材だけで、
**TCG が入っていない** (`_WL_OFFICIAL_JSON` に無い)。

検算する相手がいないので、間違った値を入れても誰も気づかない。
人が出品を見て「これ違う」と言うまで残る。それが19本。

### 実測: 今の461語を eBay 公式リストと突合すると

| | 一致 | 不一致 |
|---|---|---|
| Set | 21 | **42** |
| Rarity | 28 | **13** |

category 別 (Set): pokemon 18/32 一致、one_piece 1/11、dragonball 1/15、gundam 1/5。

**ただし不一致 = 間違い ではない。** 中身は `Awakened Pulse` (OP-06 の正式名) /
`DON Card` / `Art Rare` / `Leader` など**実在する正しい値**で、
eBay のリストが日本版セットを網羅していないだけと見られる。

## 3. 「変換表をやめる」は成立しない (検証済)

表は表記変換ではなく **判断**を持っている。

`set_name_official` は生の公式文字列 (`BOOSTER PACK -WINGS OF THE CAPTAIN- [OP-06]`)。
ここから規則で eBay 値を作れるか実測した:

```
規則 = 「-」で囲まれた部分を Title Case
ワンピース148行に適用 → 再現できたのは 1行 (147行が不一致)
```

理由は **148行のうち130行が `Promo Cards` に集約**されているため
(`1st ANNIVERSARY SET` も `8パックバトル 2023年優勝記念品` も同じ値)。
「eBay ではこれらを1つに畳む」という判断であり、規則では出せない。

畳み方はゲームで違う: one_piece は148→11種の「畳む表」、pokemon は44→32種の
「ほぼ1対1の対応表」。同じ設計で扱えるかは要検討。

## 4. 設計案

### 4.1 基本の考え方

**表を「手で書いた真実」から「照合を通った結果」に変える。**

```
今:   公式JP名 → [手書きの表] → eBay値 → 出品
              ↑ 検算する相手がいない

案:   公式JP名 → [表] → eBay値 → [eBay公式2,290語と照合] → 出品
                                    ↓ 一致しない
                              出品は止めない。「フィルタ非対応」として記録し一覧に出す
```

Set / Rarity は **FREE_TEXT** なので、リストに無い値でも出品は通る
(検索フィルタに載らないだけ)。したがって **「一致しなければ出品しない」にはしない**。
これは 2026-08-21 の Gemini レビューでも同じ指摘があった。

### 4.2 3つの状態

| 状態 | 判定 | 出品 | 扱い |
|---|---|---|---|
| A. eBay公式リストに**ある** | 一致 | 出す | 何もしない (フィルタに載る) |
| B. リストに**ない**が、公式の実在セット名 | 未収録 | **出す** | 一覧に記録。eBayへの追加申請の材料 |
| C. リストにも公式にも**ない** | 誤り | **止める** | 直す対象。ここだけが依頼になる |

B と C の切り分けは **公式データ (`set_name_official`) に在るかどうか**で機械的に決める。
人の判断を挟まない。

### 4.3 表の置き場所

- **1か所に寄せる**: rarity の二重管理 (カタログ38 / HQ15、12語重複) を解消。
  カタログを正とし、出品くん側の表は消す
- **コード内の重複を消す**: `psa_to_csv.py` / `psa_restock_csv.py` の同内容7表を1本に
  (HQ 内で完結。カタログの回答を待たない)

### 4.4 欠落の出し方

「表に無い組み合わせ」を毎日の CSV監査に載せる。今は黙って空欄になり、
人が出品を見て気づくまで分からない。

さらに、**公式に在るのに表に無い set** を定期的に洗い出す
(人が出品で躓いてから起票する順番をやめる)。

## 5. これで何本消えるか (正直に)

| 原因 | 本数 | この設計で |
|---|---|---|
| 中身が間違っている | 19 | **リストに正解がある分は消える**。ただし B (eBay未収録) は残り、依頼ではなく一覧管理に変わる |
| 表に無い (欠落) | 15 | 消える (検出 + 自動追加) |
| その他 | 31 | 一部のみ |

**ゼロにはならない。** 新しい弾が出れば表は増える。
変わるのは「人が出品で躓いて気づく」→「仕組みが先に見つける」という順番。
