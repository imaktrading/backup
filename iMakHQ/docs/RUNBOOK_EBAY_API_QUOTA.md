# eBay の API が上限で止まった時の手順書

作成: 2026-10-15 (10/14 夜の上限切れを受けて・ユーザー指示「マニュアルがなさすぎる」)
対象: 全担当 (出品くん / 監視くん / リバイスくん / ブラボー / 他の窓)

---

## 1. まず何が起きているか (1分で確かめる)

```
python iMakHQ/tools/ebay_rate_limits.py          # 残りと戻る時刻 (これ自体は枠を使わない)
python iMakHQ/tools/ebay_api_usage.py            # 今日 誰が何回呼んだか (出品くん側で数えた分)
```

- **上限は鍵ごとに1つ。呼出の種類ごとではない。** 表に GetItem / GetOrders / EndItem … と並ぶが、
  全部同じ残り数になる (Trading API 全体で 1日 5000回)。**1本の道具が使い切ると、取下げも止まる**
- 症状: ログに `exceeded usage limit` / `ErrorCode 518`。スマホに「🚨 eBay の上限に当たった」が届く
- REST の API (注文の取り込み・未発送の判定・広告・Browse) は**別枠なので止まらない**

## 2. いつ戻るか

- **米国太平洋時間の 0時** に全部戻る。待つ以外に戻す手段は無い
  - 夏時間 (3月第2日曜〜11月第1日曜): **日本 16:00**
  - 冬時間: **日本 17:00**
- 正確な時刻は `ebay_rate_limits.py` の reset 列

## 3. 止まる物と急ぎ度

| 急ぎ | 処理 | 止まると何が起きるか | 止まっている間の手当て |
|---|---|---|---|
| **高** | 監視くんの取下げ・数量0 (EndItem / ReviseInventoryStatus) | 仕入元が売切なのに買える出品が残る → 売れたらキャンセル → Defect → BAN の危険 | 監視くんの「取下げ待ち」件数を見る。0件なら待つ。**1件以上なら** 2つ目の鍵 (§5・監視くんだけ許可済) か、Seller Hub で手で数量0 |
| **中** | オファーへの返事 (GetBestOffers / RespondToBestOffer) | 期限 (約1日) 切れで売り逃し | eBay の画面 (Seller Hub → オファー) で見て返事。神風の件数は「読めない」と出る |
| **中** | バイヤーメッセージの一覧 (GetOrders / GetMyMessages) | 返事が遅れる (評価・問い合わせ対応) | eBay の画面 (メッセージ) で直接読む・返す |
| **中** | 再仕入れの数量戻し・入れ替え (ReviseFixedPriceItem) | 戻せる出品が売れない状態のまま (売り逃し・危険は無い) | 戻ってから押す |
| **低** | 新規出品の入稿 (AddFixedPriceItem) | 出品が遅れるだけ | 戻ってから入稿 |
| **低** | 値下げ・リバイス・ミラーのプロモ・CULL の段階 End | 遅れるだけ | **戻るまで回さない** (少ない残りを取下げに残す) |
| **低** | 市場調査 (market_getitem)・神風の数え直し | 表示が古いだけ | 待つ |
| 影響なし | 注文の取り込み (仕入れ待ち)・未発送の判定・FileExchange・広告 | — | — |

★残りが少ない時 (数十回) は、**高** 以外を回さない。残りは取下げに使う。

## 4. 原因を突き止めて止める

1. `ebay_api_usage.py` で今日の呼んだ数を道具別に見る (出品くん側の分)
2. 合計が上限より大きく足りない時は、**出品くん以外** (監視くん / リバイスくん) が使っている。ブラボー経由で各担当に回数を聞く
3. 犯人の定期処理を止める (タスクスケジューラ / KAGOYA の予約)。**止めるのはその担当** (他の worktree は触らない)
4. 直すまで再開しない。直す時の決まり:
   - **1件ずつ聞く処理を定期で回さない**。まとめて取れる呼出 (GetMyeBaySelling・GetSellerList) で取る
   - 回す前に **「1回の呼出数 × 1日の回数」** を出して、1日の合計に入るか確かめる
   - 走行ログに「eBay 呼出 N回」を1行出す

## 5. 2つ目の鍵 (imaktrading) について

- imax-64 が同意済みの別の鍵。上限は別枠 (5000)。うちの出品を読める・直せる (2026-10-15 実機確認)
- **eBay の規約は上限の回避を禁じている** ("Attempts to circumvent API call limits may result in termination ...
  suspension of your license")。だから**平時の増枠には使わない**
- 2026-10-15 ユーザー判断: **監視くんとリバイスくんだけ、本鍵が上限を返した時に限り使ってよい**。
  出品くん側 (自動切替 `ebay_call_usage.SWITCH_TO_SUB`) と市場調査は使わない
- 足りないのが続くなら、正規の道は eBay の **Application Growth Check** (上限を上げてもらう申請)

## 6. 戻った後にやること (16時/17時過ぎ)

1. `ebay_rate_limits.py` で残りが 5000 に戻ったか
2. 止めていた物を **急ぎの高い順** に戻す: 取下げ → オファー → メッセージ → 再仕入れ → 入稿 → 値下げ類
3. メッセージ一覧の走行ログ (`review_logs/buyer_messages.log`) の最後の行が「作り直した … eBay 呼出 N回」になっているか
4. 神風の件数 (オファー等) が「読めない」から数字に戻ったか
5. 原因の道具を直した担当は、直した後の1日の回数を報告する (ブラボーへ)

## 7. 予防 (入っている仕組み)

- `iMakeBayAPI/ebay_call_usage.py` (出品くん側の Trading の口は全部ここを通る)
  - 1本の道具は1日 **1000回まで** (取下げ・数量0 は止めない)。超えたらその道具だけ止めて **スマホに通知**
  - 合計 **3000回** を超えたら通知
  - 上限に当たったら通知
- 監視くん・リバイスくんの口はこの部品を通っていない → 各担当で同じ歯止めを入れること
