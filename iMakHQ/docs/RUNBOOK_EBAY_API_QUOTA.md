# eBay の API が上限で止まった時の手順書

作成: 2026-10-15 (10/14 夜の上限切れを受けて・ユーザー指示「マニュアルがなさすぎる」)
対象: 全担当 (出品くん / 監視くん / リバイスくん / ブラボー / 他の窓)

**順番は必ずこれ: ① 原因を突き止める → ② まず止める → ③ 急ぎの高い順に影響を数える → ④ 原因への対策 → ⑤ 復旧**
(ユーザー確定 2026-10-15)

---

## 0. 気づき方と前提

- 症状: ログに `exceeded usage limit` / `ErrorCode 518`。走行ログに「🚨 eBay の呼出: …」の行が出る (スマホには送らない・スマホの通知は仕入れ監視専用)
- **上限は鍵ごとに1つ。呼出の種類ごとではない** (Trading API 全体で 1日 5000回)。1本の道具が使い切ると **取下げも価格の直しも止まる**
- REST の API (注文の取り込み・未発送の判定・広告・Browse) は別枠で止まらない

```
python iMakHQ/tools/ebay_rate_limits.py          # 残りと戻る時刻 (これ自体は枠を使わない)
```

## ① 原因を突き止める

1. `python iMakHQ/tools/ebay_api_usage.py` — 今日 (米国太平洋0時から) 道具別に何回呼んだか (出品くん側で数えた分)
2. その合計が「5000 − 残り」より大きく足りない → **出品くん以外** (監視くん / リバイスくん) が使っている。
   ブラボー経由で各担当に「今日の Trading の回数を呼出名・道具別に」を聞く
3. 犯人の目安: **新しく入った・頻度を上げた定期処理**。直近の commit とタスクスケジューラ / KAGOYA の予約の開始日を見る
   (10/14 は KAGOYA の 20分おきの予約が当日から始まっていた)

## ② まず止める

- 犯人の定期処理を止める (タスクの無効化 / 予約を外す)。**止めるのはその担当** (他の worktree は触らない。ブラボー経由で頼む)
- 残りが少ない (数十回) 間は、**急ぎ「高」以外の eBay を呼ぶ処理を回さない**。残りは取下げと価格の直しに使う
- 止めたら「何を・いつ止めたか」を依頼書に書く (再開し忘れを防ぐ)

## ③ 急ぎの高い順に影響を数える

止まっている間に **何件・いくら** 影響が出るかを、上から順に数えて報告する。

| 急ぎ | 処理 | 止まると何が起きるか | 影響の数え方 | 止まっている間の手当て |
|---|---|---|---|---|
| **高** | 監視くんの取下げ・数量0 | 仕入元が売切なのに買える出品が残る → 売れたらキャンセル → Defect → BAN の危険 | 監視くんの「取下げ待ち」件数 (売切を検知したのに eBay に送れていない行) | 0件なら待つ。1件以上なら 2つ目の鍵で送る (§⑤-2・自動で切替) / それも駄目なら Seller Hub で手で数量0 |
| **高** | リバイスくんの価格の直し (仕入値の変化 → 出品価格) | 仕入値が上がったのに eBay の値段が安いまま → **売れたら赤字** | 監視くんが仕入値を書き換えたのにリバイスが送れていない行の数と、そのうち今の値段で赤字になる行の数・赤字額 | 2つ目の鍵で送る (§⑤-2・自動で切替) / それも駄目なら赤字になる行だけ Seller Hub で手で値上げ |
| **中** | オファーへの返事 | 期限 (約1日) 切れで売り逃し | Seller Hub のオファー画面の件数と期限 (神風は「読めない」と出る) | Seller Hub で返事 |
| **中** | バイヤーメッセージ | 返事が遅れる | eBay のメッセージ画面の未返信数 | eBay の画面で読む・返す |
| **中** | 再仕入れの数量戻し・入れ替え | 戻せる出品が売れない (売り逃しのみ) | 神風の「再仕入れ」の件数 | 戻ってから押す |
| **低** | 新規出品の入稿 | 出品が遅れるだけ | 入稿待ちの CSV の行数 | 戻ってから入稿 |
| **低** | 値下げ・ミラーのプロモ・CULL の段階 End | 遅れるだけ | — | 戻るまで回さない |
| **低** | 市場調査・神風の数え直し | 表示が古いだけ | — | 待つ |
| 影響なし | 注文の取り込み・未発送の判定・FileExchange・広告 | — | — | — |

## ④ 原因への対策

1. 犯人の処理を直すまで再開しない。直す時の決まり:
   - **1件ずつ eBay に聞く処理を定期で回さない**。まとめて取れる呼出 (GetMyeBaySelling・GetSellerList) で取る
   - 入れる前に **「1回の呼出数 × 1日の回数」** を出し、他の処理と合わせて 5000 に入るか確かめる (超えるなら入れない)
   - 走行ログに「eBay 呼出 N回」を1行出す (0回でも)
2. その処理を通る口に歯止めがあるか確かめる (§予防)。無ければ同じ物を入れる
3. 依頼書に「原因 / 止めた物 / 影響の数 / 対策 / 直した後の1日の回数」を残し、下の「過去の事例」に1行足す

## ⑤ 復旧

### ⑤-1 いつ戻るか
- **米国太平洋時間の 0時** に全部戻る。待つ以外に戻す手段は無い
  - 夏時間 (3月第2日曜〜11月第1日曜): **日本 16:00** / 冬時間: **日本 17:00**
  - 正確な時刻は `ebay_rate_limits.py` の reset 列

### ⑤-2 2つ目の鍵 (imaktrading) — 緊急時に急ぎ「高」の処理だけ
- imax-64 が同意済みの別の鍵 (上限は別枠 5000)。うちの出品を読める・直せる (2026-10-15 実機確認)
- **2026-10-15 ユーザー確定: 本鍵が上限を返した緊急時は、急ぎ「高」の処理 (③の表の「高」= 取下げ・数量0 / リバイスの価格の直し) は2つ目の鍵を使う**。
  ユーザー: 「別アカウントの運営も行っているので取得している。不正な処理をするために取得しているわけではないから問題ない」
  - 監視くん: 取下げ・数量0 を本鍵が 518 の時だけ2つ目の鍵で送り直す (入れ済)
  - リバイスくん: 本鍵が 518 を返した日だけ2つ目の鍵 (入れ済・上限は KAGOYA 1,200 / 家 300 のまま)
- 「中」「低」の処理と平時は本鍵だけ (出品くん側の自動切替 `ebay_call_usage.SWITCH_TO_SUB = False`・市場調査も本鍵)
- 2つ目の鍵で送った回数は各担当の走行ログに出す。足りない状態が続くなら eBay の **Application Growth Check** (上限を上げる申請)

### ⑤-3 戻った後にやること
1. `ebay_rate_limits.py` で残りが 5000 に戻ったか
2. 止めていた物を **急ぎの高い順** に戻す: 取下げ → 価格の直し → オファー → メッセージ → 再仕入れ → 入稿 → 値下げ類
3. ③で数えた影響が0件になったか確かめる (取下げ待ち0 / 赤字の行0)
4. メッセージ一覧の走行ログ (`review_logs/buyer_messages.log`) が「作り直した … eBay 呼出 N回」に、神風のオファー件数が数字に戻ったか
5. 原因の処理は ④ の対策が入ってから再開する。再開した日の1日の回数をブラボーに報告

## 予防 (入っている仕組み)

- `iMakeBayAPI/ebay_call_usage.py` (出品くん側の Trading の口は全部ここを通る)
  - 1本の道具は1日 **1000回まで** (取下げ・数量0 は止めない)。超えたらその道具だけ止めて **走行ログに1行**
  - 合計 **3000回** を超えた時・上限に当たった時も走行ログに1行 (スマホには送らない)
- 監視くん・リバイスくんの口はこの部品を通っていない → 各担当で同じ歯止めを入れること
